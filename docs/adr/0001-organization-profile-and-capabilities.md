# ADR 0001 — Профиль организации и права (capabilities)

**Статус:** предложено · **Этап:** 1А ([ROADMAP](../ROADMAP.md)) · **Владелец:** skyze · **Дата:** 01.10.2026

## Проблема

Кто что может в ассистенте, решается разрозненно: админка — по ответу сервера `is_admin()`, панель лидера —
по роли, ИИ — доступен всем. Впереди функции, которым нужна одна модель прав: вход для ИИ через сервер
(этап 4), практика по организациям (6А), режим отладки для админа (7Б), команды в быстром поиске (2В), позже —
разграничение по организации. Без общей модели каждая функция заведёт своё условие в интерфейсе, а
организации будут добавляться правкой кода.

## Текущая реализация

- `Organization` в пакете (`src/core/model.ts`): `id`, `name`, `kind` (`state` | `crime`), `documents` —
  документы, которые у членов организации идут первыми. Берётся из `data/<server>/organizations.json`
  (`src/importer/buildPack.ts`).
- Организацию игрок выбирает сам; она ничем не подтверждена.
- Роли — `leader`, `deputy` (`src/account/roles.ts`), админ — `is_admin()`. Что можно делать с ролями, решают
  правила базы (RLS), `src/ui/roles.tsx` кэширует роли для работы без сети.
- Провайдер ИИ — `ai.provider`: `server` (наш сервер), `gemini` или `custom` (ключ и деньги игрока).

## Предлагаемая реализация

1. **Права — чистая функция**, без React и сети, в `src/account/capabilities.ts`:

   ```ts
   type Capability =
     | 'ai.server'        // ИИ через наш сервер
     | 'ai.own-key'       // ИИ со своим ключом (gemini, custom)
     | 'sync'             // синхронизация с аккаунтом
     | 'memos.read' | 'memos.write' | 'faction.deputies'
     | 'admin.roles' | 'ai.admin_debug';

   function capabilitiesOf(input: {
     signedIn: boolean;
     roles: Role[];            // роли на текущем сервере и в текущей организации
     admin: boolean;
     organization?: Organization;
   }): Set<Capability>;
   ```

   Таблица «профиль → права» — в `ROADMAP_ARCHITECTURE.md` §5, тесты — по каждой её строке.
2. **Хук `useCapabilities()`** в `src/ui/roles.tsx`: интерфейс спрашивает «есть ли право», а не «лидер ли
   это». Существующие проверки (админка, панель лидера, памятки) переходят на него.
3. **Профиль организации — поля того же `Organization`**, только с читателем: `training?` (учебные наборы для
   практики, этап 6А), `quickActions?` (быстрые действия на главной и в командах, этап 2В). Поле без читателя
   не добавляется.
4. **Организация ничего не закрывает.** Она меняет, что показано первым. Закрывают вход, роли, выданные
   админом, и сервер (правила базы, сервер ИИ после этапа 4).

## Альтернативы

- **Права в пакете сервера по ролям.** Отклонено: роли выдаются в базе и проверяются там; пакет одинаков для
  всех игроков сервера и обновляется с законами — права в нём смешали бы два источника правды.
- **Права по организации сразу.** Отклонено: организация не подтверждена, закрыть по ней — не защита
  (ADR 0008, позже).
- **Оставить условия в интерфейсе.** Отклонено: каждая новая функция добавит своё, сервер ИИ не сможет
  переиспользовать модель.

## Плюсы

- Одна точка правды для показа функций; сервер ИИ на этапе 4 проверяет те же права.
- Новая организация — строка в `organizations.json`, без кода.
- Функция чистая — тестируется таблицей, без интерфейса.

## Минусы

- Права в клиенте — только показ; до этапа 4 ИИ через сервер фактически открыт.
- Ещё один слой между ролью и интерфейсом.

## Миграция

Новые поля `Organization` необязательные — `PACK_FORMAT` не поднимается, старые копии их не читают. Данные
игроков не меняются. Существующие проверки переводятся на `useCapabilities()` без смены поведения —
существующие тесты должны пройти без правок.

## Риски

- Раздуть профиль «на будущее». Защита — правило «поле вместе с читателем» и ревью.
- Расхождение прав в клиенте и на сервере после этапа 4. Защита — сервер ИИ использует тот же список
  `Capability` (общий JSON или тест, сверяющий оба списка).

## Rollback

Один PR на задачу; откат возвращает прежние условия. Данных не трогает.
