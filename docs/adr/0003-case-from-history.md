# ADR 0003 — «Дело» из «Истории»

**Статус:** предложено · **Этап:** 5 ([ROADMAP](../ROADMAP.md)) · **Владельцы:** AidenArokij (ИИ, `CaseState`),
skyze (хранение, синхронизация, Supabase, PRIVACY) · **Дата:** 01.10.2026 · **Начинается:** когда за «Дела»
возьмётся Айден, после новой архитектуры ИИ

## Проблема

Игрок разбирает ситуацию, добавляет статьи в калькулятор, уточняет факты — но результат живёт в разговоре, у
которого нет названия, его нельзя закрепить, найти, продолжить на другом ПК, и не видно, по какой базе он был
сделан. Промпт roadmap просит сущность «Дело» — но без второго механизма хранения и без второго `CaseState`.

## Текущая реализация

- `CaseState` (`src/protocol/context.ts`): `facts`, `assumptions`, `norms`, `articles` (id), `conclusion`.
  Каждый ответ оставляет его; следующий вопрос, «уточнить» или «исправить» анализируются относительно него.
- Разговоры сохраняются в «Историю» (`src/ui/ai.ts`, `StoredConversation`, ключ на сервер), только на этом
  компьютере; при открытии статьи проверяются заново.
- Калькулятор — отдельное состояние главного окна (`Overlay.tsx`), с разговором не связан.

## Предлагаемая реализация

1. **«Дело» = сохранённый разговор + развитый `CaseState`.** `StoredConversation` получает: `title`,
   `pinned`, `archived`, `charges` (ключи статей калькулятора и штраф), `snapshot` (`label` пакета и
   отпечатки статей дела, этап 1Б), `history` (изменения фактов). `CaseState` — поля, нужные ИИ; то, что ИИ не
   нужно (название, закрепление), — в `StoredConversation`.
2. **Изменение факта** → разбор заново (как «исправить» сейчас) → приложение сравнивает старый и новый
   `CaseState` детерминированно и показывает «было → стало» по фактам, нормам, наказанию (калькулятор) и
   выводу. Графа «факт → вывод» нет: выводы пишет ИИ, связь в тексте ненадёжна.
3. **Снимок базы**: при открытии дела отпечатки его статей сверяются с текущим пакетом; если отличаются —
   «Изменилось после создания дела» и «Проверить по текущей базе».
4. **Действия** — контекстные, в самом деле: переименовать, закрепить, в архив, дублировать, поиск по делам,
   «скопировать как текст» (экспорт).
5. **Хранение** — на компьютере, как сейчас. **Синхронизация** — галочкой в настройках: таблица Supabase с
   правилами «видит только владелец», `PRIVACY.md` и README в том же PR.
6. **В интерфейсе** — «История» в разделе «ИИ» переименовывается в «Дела»; макет C не меняется.

## Альтернативы

- **Новая сущность «Дело», где разговор — одна из частей** (статьи и расчёты без ИИ). Отложено: сначала
  проверить, пользуются ли делами; перейти можно позже, данные совместимы.
- **Граф зависимостей «факт → статья → вывод».** Отклонено (см. п. 2).
- **Синхронизация по умолчанию.** Отклонено: тексты разборов — самое чувствительное у игрока.

## Плюсы

- Один `CaseState`, одно хранилище — без второго механизма.
- Снимок почти бесплатный: версия пакета и отпечатки уже есть после этапа 1Б.
- Старые разговоры становятся делами без потери данных.

## Минусы

- Дело привязано к ИИ-разговору; дело «только с калькулятором» — позже.
- Синхронизация добавляет таблицу и новые данные на сервере.

## Миграция

- Старые `StoredConversation` читаются как дела: `title` — первый вопрос (как сейчас в «Истории»),
  `snapshot` — пустой («база на момент создания неизвестна»).
- Формат хранения версионируется полем `version` в записи; чтение старых записей покрыто тестом.

## Риски

- Размер локального хранилища при длинных делах — ограничить число неархивных дел или длину истории изменений.
- Утечка текстов при синхронизации — RLS «только владелец», тест правил в миграции, выключено по умолчанию.

## Rollback

Новые поля необязательные: откат приложения читает дела как прежнюю «Историю». Синхронизация выключается
галочкой; таблица остаётся до решения владельца.
