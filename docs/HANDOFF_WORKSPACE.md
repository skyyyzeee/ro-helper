## Как собрать и восстановить

В рабочем клоне:

```powershell
git status --short
git switch codex/search-workspace
npm ci
pwsh -File scripts/build-workspace.ps1
```

`npm ci` нужен, если зависимости отсутствуют. Скрипт сам собирает frontend, подставляет `src-tauri/tauri.preview.conf.json`, запускает **cargo build --release --features tauri/custom-protocol**, затем проверяет версию и актуальность встроенных assets. Нужны Rust, Windows Build Tools, Node.js и cargo в PATH. Нативная сборка занимает примерно 3–5 минут.

Важно: один `cargo build --release` БЕЗ `tauri/custom-protocol` в этом проекте может собрать окно, открывающее dev URL `127.0.0.1:1420`, а не автономное приложение. Пользоваться подготовленным скриптом. Не менять production identifier/ключ подписи ради превью.

Клон shallow. Резервный bundle содержит нашу ветку поверх базового `697063a`; для восстановления коммитов нужен репозиторий с этим базовым коммитом. В свежем клоне upstream с доступным основанием:

```powershell
git fetch 'C:/Users/sed19/Downloads/protocol-handoff/claude_code_package/protocol-app/artifacts/workspace-preview/workspace-work.bundle' codex/search-workspace:codex/search-workspace
git switch codex/search-workspace
```

Если Git-восстановление пока недоступно, `workspace-source.zip` содержит весь код для сборки. Не продолжать в старом `protocol-app/src` по ошибке. Не выполнять автоматически старый план с fast-forward/merge из октябрьского раздела передачи поверх этой рабочей ветки.

При UI-проверке читать текущий снимок окна. Windows accessibility иногда возвращает старую структуру сразу после действия; свежий screenshot показывает реальный результат. Если пользователь сам управляет окном — не бороться за мышь. При пересборке завершать только тестовый процесс по точному пути; установленную production-копию не трогать.

## Порядок продолжения после паузы

### Сначала продолжить незавершённую работу приложения

Не считать текущую задачу закрытой и не заменять её исследованием ИИ. Готова первая итерация калькулятора, а не весь калькулятор и не вся переработка приложения. Продолжить с места остановки:

- Сделать итог удобным при длинном списке обвинений: результат должен легко находиться, список и объяснения не должны мешать основным действиям.
- Доработать и проверить смешанные наборы УК/КоАП: раздельные итоги и единое обвинение, изменения состава, переключения наказаний, копирование и рапорт.
- Проверить масштаб текста, длинные названия и списки, минимальную ширину и возврат к источнику в собранном Windows-приложении; исправить найденные проблемы. Не повторять уже готовые изменения вместо оставшихся.
- Затем по порядку продолжить ещё не переработанные «Отдел», ИИ-сценарии интерфейса, вики и закреплённые карточки. Перед итоговым PR упорядочить добавленные стили и проверить общие состояния интерфейса.

Следующий конкретный шаг — локальная практика и состояния загрузки/ошибки. Чтение ответа и возврат из источника исправлены и проверены тестами; нативная проверка заполненной истории и длинного ответа ещё нужна перед PR. Затем вики, закреплённые карточки и общая уборка CSS. Отдельное исследование архитектуры/моделей остаётся незавершённым.

### Отдельная задача: архитектура ИИ и выбор модели / API

Пользователь отдельно попросил пересмотреть, как работает ИИ: хочется стабильных хороших ответов, желательно на сильной бесплатной модели либо через недорогой API. Это задача исследования и проверки; подходящий вариант пока не выбран. Не обещать бесплатность, качество или доступность без актуальных данных.

1. Прочитать `src/protocol`, `server/`, `src/ui/ai.ts` и документацию `docs/AI_PIPELINE.md`, `SOURCE_GROUNDING.md`, `AI_CLASSIFIER.md`, `AI_EVALUATION.md`, `AI_DATASET.md`, `AI_ACCESS.md`. Восстановить фактический путь запроса: классификация → область источников → поиск и контекст → вызов модели → проверка → ответ / отказ → история. Проверить реальные конфигурации моделей и резервных провайдеров по коду, не полагаться на старые названия в заметках. Ключи и `.env` не выводить.
2. Снять исходные показатели. Разделить ошибки поиска источников, нехватку контекста, ошибки рассуждения модели, неподтверждённые утверждения и потери полезного ответа из-за проверки. Отдельно разобрать многотуровые уточнения, неоднозначность ситуации и отсутствие нормы в базе. Сначала найти причину слабых ответов, затем решать, где менять архитектуру и где модель.
3. По актуальным официальным источникам сравнить бесплатные облачные тарифы, локальные модели и дешёвые платные API. Зафиксировать дату, точные model IDs, цены входа/выхода, квоты и ограничения, контекст, структурированный JSON, задержки, доступность из РФ, условия обработки данных. Локальный вариант оценивать с учётом реального оборудования и потребления памяти, бесплатный API — с учётом лимитов и пригодности для нескольких пользователей. Бюджет и целевая нагрузка пока не заданы: явно записать допущения либо уточнить их при возобновлении.
4. Сравнить кандидатов на одинаковом наборе наших русскоязычных сценариев и одной версии базы. Использовать существующие offline/live eval; добавить повторные прогоны одинаковых запросов для измерения стабильности, а не выбирать по одному удачному ответу. Оценивать подтверждённость источниками, правильность статьи/части, полезность объяснения, корректный отказ, следование JSON, задержку и стоимость на типичный/длинный запрос. Для цены на месяц указать сценарии нагрузки; учитывать повторные попытки и резервную модель. Инъекции и смешение источников оставить обязательными проверками.
5. Представить конкретный вариант архитектуры, основную модель и резерв, затраты и ограничения, затем план небольших проверяемых изменений. Не менять провайдера вслепую ради более сильного названия. Сохранить принцип: ИИ работает поверх выбранной базы сервера и ссылается на источники, наказание считает калькулятор. Ключи остаются на сервере. Изменения отправки/хранения данных отражать в PRIVACY/README. Изменения промптов, классификатора, схемы, проверок или модели сопровождать сравнением eval до/после; целевой CONFIRMED_HALLUCINATION_RATE — 0, без проваленных обязательных проверок. Платные массовые прогоны планировать с понятным объёмом и бюджетом.
