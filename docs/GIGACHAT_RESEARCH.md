# GigaChat в RP-разборе

## Что уже работает

- Ассистент выбирает пакет нормативной базы активного сервера, ищет статьи и передаёт найденные фрагменты с идентификаторами. Проверка ссылок, частей и цифр выполняется после генерации. Прямой вопрос о наказании может получить ответ из базы без запроса к модели. См. [конвейер](../src/protocol/pipeline.ts), [проверку источников](SOURCE_GROUNDING.md) и [валидатор](../src/protocol/validate.ts).
- Быстрый режим передаёт до 8 основных источников, подробный до 14. Проверка поиска по 14 источникам сама по себе не покрывает быстрый режим. Для него нужно проверять фактический набор источников в запросе к тестовой модели. См. [конвейер](../src/protocol/pipeline.ts) и [тест поиска](../src/protocol/recall.test.ts).
- Сервер уже измеряет ожидание в очереди и время вызова модели, кэширует готовые ответы по полному запросу и разбирает JSON GigaChat после ответа. Прямой вызов GigaChat пока не передаёт схему ответа. См. [сервер](../server/server.mjs) и [экзамен](AI_EVALUATION.md).

## Что проверять на GigaChat

1. **Схема ответа.** Сбер документирует JSON Schema для обоих форматов API. В v1 параметр передаётся в `response_format`, в v2 внутри `model_options`. Проверить поддержку на конкретной модели и адресе перед включением. Схема ограничивает форму ответа. Проверка ссылки на статью текущего сервера остаётся у ассистента. [Структурированный вывод](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output)
2. **Размер запроса и ответа.** Сначала измерить расход на одинаковых сценариях. Сбер рекомендует снижать температуру для более предсказуемых ответов и описывает `max_tokens` как предел генерации. Уменьшать бюджет по результатам замеров. Слишком низкий предел может обрезать JSON и привести к дополнительному вызову. [Руководство по промптам](https://developers.sber.ru/help/gigachat-api/prompt-engineering) · [Подсчёт токенов](https://developers.sber.ru/docs/ru/gigachat/guides/counting-tokens)
3. **Повторный контекст.** `X-Session-ID` помогает GigaChat использовать кэш, если идентификатор и часть контекста совпадают. Проверять отдельно от кэша готовых ответов, по `precached_prompt_tokens` и задержке повторных запросов. [Контекст и кэширование](https://developers.sber.ru/docs/ru/gigachat/guides/keeping-context)
4. **Задержка.** Для физлиц GigaChat документирует один поток. Измерять отдельно очередь и генерацию. Потоковая выдача позволяет получать токены до завершения генерации. Готовый RP-вердикт можно показывать после проверки целого ответа и его источников. [Квоты](https://developers.sber.ru/docs/ru/gigachat/limitations) · [Потоковая генерация](https://developers.sber.ru/docs/ru/gigachat/guides/response-token-streaming)

Перед сравнением зафиксировать версию нормативных пакетов, модель, режим и набор сценариев. Для каждого варианта измерить долю верных ответов, число ошибок формата и подтверждённых выдумок, число запросов к модели и p50/p95 времени до проверенного ответа. Холодные запросы и попадания в кэш считать отдельно. Включить обычные ситуации и сценарии с чужим сервером, неверным номером статьи, уточнением и незнакомой нормой. Тесты с подставной моделью покрывают проверку источников без расхода токенов. Замеры качества и задержки GigaChat требуют живого прогона.

### Пробный прогон требований адвоката

В окружении должны быть заданы `GIGACHAT_AUTH_KEY` и доверенные сертификаты, если они нужны для подключения. Используйте одну модель, одинаковые номера кейсов и один коммит.

```powershell
npm run eval -- --gigachat --model GigaChat-2-Max --cases 107,137
Copy-Item eval/results/last.json eval/results/gigachat-default.json
npm run eval -- --gigachat --gigachat-schema --model GigaChat-2-Max --cases 107,137
```

Второй прогон включает строгую схему ответа для проверки требований адвоката. Ошибка поддержки схемы остаётся ошибкой эксперимента. Сравните число пройденных кейсов, ошибки связи и формата, p50 и p95 и отпечатки баз в двух отчётах. Два кейса подходят для проверки совместимости. Для оценки скорости нужен повторный прогон на более широкой выборке.

## Итог проверки 8 ноября 2026

Два сравнительных прогона: 10 одинаковых ситуаций, три сервера, одинаковые отпечатки базы, быстрый режим, обычный формат.

| Модель | Первый прогон | Повтор | Медиана в повторе |
| --- | ---: | ---: | ---: |
| GigaChat-2-Max | 9/10 | 8/10 | 3,97 с |
| GigaChat-3-Ultra | 9/10 | 9/10 | 2,87 с |

Обе модели не прошли №31 в обоих прогонах. В повторе Max также не прошёл №112: ответ о задержании опирался на КоАП 18.3, хотя в переданных источниках был УПК 52. Разобрать №31 отдельно: в сохранённых отчётах нет текста ответа по нему.

На двух сценариях требований адвоката (№107 и №137) обычный формат дал 2/2 у обеих моделей; строгая схема — 1/2 у Max и 0/2 у Ultra. В этом PR схема остаётся режимом локального экзамена. Модель на сервере не меняем: Ultra быстрее в этой выборке, но на предыдущем расширенном сравнении Max набрал 26/26, Ultra — 22/26.

Повторить сравнение из корня репозитория: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-gigachat-exam.ps1 -Compare`. При первом вводе Windows сохраняет ключ в зашифрованном виде под текущей учётной записью. Для замены ключа добавьте `-ResetKey`.
